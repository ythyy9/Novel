目前的需求已经足够形成第一版架构。我的建议是：
建立一套“以本地项目资料为长期记忆、以可替换 Agent 为执行者、以独立检查和读者反馈为改进依据”的小说创作系统。
Codex 是第一任执行者；小说、经验、规则和进度属于项目，不属于某一次对话或某一家模型。

下面是架构方案，而不是已经实现或验证完成的系统。

## 一、先明确：我们究竟在建设什么

你要的系统，不是把外国小说逐章改写成中文版，也不是先设计一个庞大的写作软件，再期待它自动生成好作品。
它的核心任务是：
从参考作品中学习有用的叙事方法，为中国目标读者创造新故事；在人物与世界的因果关系约束下探索后续，逐章写作、审核、返修，并从这些过程中改进自己的工作方法。
其中有三个不可混淆的目标：

| 目标 | 具体含义 |
| --- | --- |
| 作品持续改善 | 人物更鲜明，情感更有形成过程，环境更有生活感，剧情更经得起推敲。 |
| 系统能力持续改善 | 能发现以前漏掉的问题，减少重复犯错，知道哪些修改有效、哪些越改越差。 |
| 执行过程可靠 | 换对话、换 Agent、运行中断，都不会丢失进度、混淆版本或绕过你的原则。 |



**第三项可以较多依靠程序验证；第一、第二项还必须通过实际作品和反馈检验。**不能因为自动流程全部运行成功，就宣称小说写好了。

## 二、总体结构：稳定的控制层，连接两个迭代循环

我建议把系统分成四层，而不是一开始设置十几个互相讨论的“专家 Agent”。

| 层次 | 负责什么 | 谁来执行 |
| --- | --- | --- |
| 原则与授权层 | 创作原则、明确锁定的内容、费用边界、暂停条件 | 你决定，程序保护 |
| 运行控制层 | 分配任务、管理版本、跨会话接续、验证结果、失败恢复 | 轻量本地调度脚本 |
| 创作与研究层 | 原作分析、人物推演、正文写作、跨领域研究、审稿与返修 | Codex，未来可替换 |
| 项目与经验层 | 正文、设定、事件、研究依据、审稿案例、历史决策 | 本地文件和结构化记录 |



运行控制层连接两个循环：
作品循环：
当前人物与世界状态 → 探索下一步 → 写作 → 审核 → 研究或返修 → 阶段性通过 → 更新状态 → 下一章。

系统改进循环：
收集反复出现的问题 → 提出原因假设 → 修改工作方法或工具 → 对照验证 → 保留或回滚。

**两个循环必须分开。**不能让正在写某一章的 Agent，顺手把审核标准改低，再宣布这一章通过。

## 三、长期记忆：不是一份超长总结，而是有来源、有状态的项目资料

这是整个系统最重要的基础。

### 1. 建议的目录结构


```text
novel-system/
├─ AGENTS.md                  # 简短入口：项目地图与工作规则索引
├─ adapters/                  # Codex、未来其他 Agent 的接入方式
├─ controller/                # 调度、校验、接续与停止控制
├─ policies/                  # 你的原则、授权边界、锁定项
├─ methods/                   # 可迭代的创作、研究、审稿方法
├─ evaluations/               # 评估案例、基准版本、对照结果
├─ lessons/                   # 跨作品可复用的经验
│
├─ books/
│  └─ book-001/
│     ├─ reference/           # 原作分析与参考材料索引
│     ├─ canon/               # 当前采用的世界事实与人物记录
│     ├─ manuscript/          # 当前有效正文
│     ├─ possibilities/       # 尚未采用的剧情候选
│     ├─ research/            # 外部资料、证据与适用范围
│     ├─ reviews/             # 审稿发现、处置与复核
│     ├─ decisions/           # 你的决定及其上下文
│     └─ revisions/           # 重要返修的原因、范围和结果
│
└─ runtime/                   # 任务队列、运行状态、交接记录
```


正文和需要人阅读的资料优先使用 Markdown；需要程序验证的任务、事件、问题记录使用结构化格式。运行队列可以使用本地 SQLite。这些是建议选型，不需要先建设复杂数据库平台。
AGENTS.md 只负责告诉执行者“去哪里找到什么”，不塞入全书设定。Codex 官方支持通过 AGENTS.md 加载项目指令；Harness Engineering 文章也明确采用短入口加结构化知识库的方式。OpenAI Developers

### 2. 必须区分六种“知道”

你的小说尤其需要避免把下面这些内容混在一起：

| 信息类别 | 示例 |
| --- | --- |
| 作品已采用的事实 | 某次袭击确实由甲组织实施。 |
| 人物掌握的信息 | 乙只知道袭击发生，不知道幕后主使。 |
| 人物的错误认识 | 乙误以为幕后主使是丙。 |
| 读者已经获得的信息 | 读者看到过甲的异常行动，但尚未得到确认。 |
| 作者尚未决定的内容 | 另一场事件的幕后主使暂时没有确定。 |
| 未采用的候选方案 | 系统曾考虑让丁背叛，但最终没有采用。 |



错误认识可以推动剧情；信息混淆则会毁掉剧情。
系统不能把“曾经讨论过让丁背叛”记成“丁已经背叛”，也不能让乙使用只有作者知道的信息作决策。
此外，每条重要记录都应能追溯到正文、你的决定或设定文件。总结只是检索入口，不能替代原始依据。

### 3. 正文和记忆必须一起更新

假设系统把第八章的一次争执改成了和解，那么人物关系、后续误解、审稿记录都可能受到影响。
因此，一次重要返修应当形成一个完整的版本变更：
正文修改＋相关状态修改＋受影响章节清单＋复核结果。

不能正文已经改了，人物档案仍保留旧事实；也不能把旧版本的审稿结论继续用于新版本。

## 四、创作核心：人物与世界驱动，参考作品不拥有最终决定权


### 1. 原作分析要产出“方法”，不是复制路线

原作分析模块应分别记录：
原文发生了什么、这一段可能发挥了什么作用、这种作用依赖哪些条件、哪些经验值得借鉴。
例如：
原作通过一次共同隐瞒秘密，让两个原本敌对的人建立脆弱的同盟。

系统可以借鉴“共同承担风险如何改变关系”，但不能因此规定新故事也必须出现同样的秘密和事件。
当新人物与世界不支持这个结构时，应当允许放弃它。原作分析不进入新作品的事实库，也不自动成为后续章节的任务清单。
《安珀志》目前仍然是候选参考作品，不应写死在系统架构里。

### 2. 人物档案不是“性格标签”，而是持续变化的行动依据

“聪明、冷静、重感情”不足以指导长篇创作。
我建议主要人物至少维护这些内容：他想得到什么、最怕失去什么、有哪些承诺和牵制、掌握什么信息、具备什么资源、如何理解其他人，以及哪些经历改变了他的判断。
同样面对一次背叛，三个聪明人可能采取不同策略：
一个人优先保住组织，因此暂时隐忍。
一个人不能容忍失去控制，因此立即反击。
一个人更在意家人安全，因此选择撤退。

这些只是设计示例。关键不在于给每人贴一个固定反应，而是让选择能够追溯到这个人此时的价值排序、认识与处境。
人物成长也要体现为这些记录的变化，而不只是能力等级上升。

### 3. “配角不能待机”需要独立的事件记录

我建议采用按事件推进的幕后演进，不逐分钟模拟全世界。
例如，主角离开一座港口六周，留在当地的对手有自己的债务、盟友和竞争压力。再次出场前，系统需要检查：这六周有哪些条件变化？他做过哪些选择？哪些结果已经影响到当前剧情？
但也不能反过来强迫每个配角不断制造大事件。主动等待也可以是合理选择，只是等待必须有理由，期间获得的新信息也应影响其判断。
幕后演进首先作为候选推演；被采用后才进入世界事实。不能每次需要一个反转，就临时声称配角早已在幕后完成了一切。

### 4. 世界是相互影响的条件，不只是设定百科

世界记录需要表达关系：
某地的地形和环境条件 → 可获得的资源与交通条件 → 人们的生产生活 → 组织的利益 → 人物能够作出的选择。

具体关系是否成立，需要查证或按作品规则推演，不能预先假装存在一套万能公式。
奇幻规则可以不同于现实，但系统要检查它的后果。例如，一种能力如果显著改变运输成本，就需要追问世界中的贸易和权力安排为何仍是当前样子。不能只在主角需要时，这种能力才对社会产生作用。

## 五、逐章工作流程：先写好这一章，但不把未来全部锁死

你的偏好是探索式创作，因此我建议采用“近处具体、远处开放”的推进方式。

### ① 恢复当前状态

读取当前有效正文、相关人物经历、未解决问题、重要幕后事件和你的锁定项。
不是每次把整本书塞进上下文，而是先检索，再回到必要的原文核对。

### ② 推演下一步

从现有冲突、人物目标和环境变化提出少量有实质区别的走向。
普通、可回滚的选择可以自主作出。涉及你锁定的方向，或出现系统无法解决的重要分歧，才请求你决策。

### ③ 形成当前章节的写作意图

明确这一章主要发生什么变化：人物关系、认识、局势、情绪或读者理解有什么推进。
**不要求每章都有反转、爆点或相同的情绪曲线。**安静的一章也可以有必要性，不能让“章节任务书”变成模板化写作。

### ④ 写作与分层审核

先写出可以完整阅读的正文，再分别检查事实因果、人物情感、世界条件与阅读体验。
审核角色是不同的任务职责，不必对应不同模型或并发进程。第一版可以由现有 Agent 在不同会话中依次执行。

### ⑤ 定向返修与影响检查

修复已经确认的问题，避免每收到一条意见就重写全章。
返修前明确要改善什么；返修后检查是否真的改善，以及是否破坏了其他优点。

### ⑥ 阶段性通过，进入下一章

已确认的原则性错误没有解决，不得通过。
重大争议解决不了，暂停请你决定；局部难分优劣的问题，保留较好的版本、记录疑问后继续。
**通过的只是当前版本，不是永久定稿。**出现重要回改时，受影响章节的旧审核结论要重新检查。

## 六、审核系统：不能只问“有没有人味，打几分”

我建议把审核分成三类，避免将性质不同的问题合并成一个总分。

| 审核类别 | 典型问题 | 处理方式 |
| --- | --- | --- |
| 明确错误 | 人物提前知道秘密；事件顺序冲突；正文与已采用设定不一致 | 给出位置和证据，确认后阻止通过 |
| 合理性疑点 | 动机依据不足；环境条件是否支持某种生活方式尚不明确 | 定向核查、研究或要求补充前提 |
| 阅读体验判断 | 人物声音相似；情绪没有落地；环境描写让人难以进入场景 | 提供具体阅读依据，比较版本，保留不确定性 |



一份有效的审稿意见，应当至少说清楚：
问题在哪里；依据是什么；影响有多大；可能如何修改；改动会影响哪些其他内容。

“这里缺乏人味，建议增加细节”不够。
更有用的意见是：
正文说两人多年互不信任，但此处甲在没有新证据、没有利益交换、没有情感触发的情况下，把最重要的信息直接交给乙。需要确认这是有意的冒险，还是缺少转变过程。


### 主观质量用“诊断＋比较”，不靠分数冒充客观结论

针对你的审美，初期重点检查三件事：
环境是否通过人物的活动被体验到，而不只是景物清单；情感变化是否由经历与互动支撑；不同人物是否表现出可区分的关注点和选择方式。
这些是诊断方向，不是机械的写作公式。不能演变成“每段必须有感官描写”“每章必须出现情绪转折”。
比较修改前后版本时，建议隐藏哪个是新版、交换展示顺序，并允许结论是“各有优缺点”或“没有明确改善”。OpenAI 的评估指南指出，模型评审存在展示顺序偏差和偏爱较长回答等问题，并建议使用成对比较、具体标准及人类校准。OpenAI Developers
**新的审稿会话也不是独立真人读者。**第一阶段需要把你的样章反馈积累为具体案例，之后再引入目标读者，校准系统的判断。

## 七、自主研究：研究的是条件和依据，不是给剧情补借口

研究模块由具体问题触发，不进行无目标的百科搜集。
例如：
当前事件依赖“消息能在两天内传到另一座城市”，但项目没有确定距离、交通方式和中间障碍。

系统应先识别缺少哪些前提，再查资料或计算，而不是直接寻找一个能证明“两天可达”的例子。
研究记录需要保存：问题、来源、结论、适用范围、尚未确定的条件，以及它影响哪些设定或章节。还要区分外部资料支持的事实、系统自己的推断、作品自行设定的规则。
两个边界尤其重要：
**心理学不能变成人物行为的统一模板。**没有作出最优选择，不等于动机不合理；需要检查这个人物当时为何会如此行动。
**地理等领域的审核不能假装精确。**关键环境条件尚未确定时，应报告条件不足，或者给出带前提的定性判断，而不是生成一份看起来专业、实际无法支撑的结论。
研究优先服务于会影响人物选择、关键事件和世界运行的问题。无关紧要的细节不应无限消耗创作资源。
外部网页和下载材料只作为资料，不能成为指挥 Agent 修改权限、运行陌生程序或上传项目文件的指令。

## 八、系统如何“越做越好”：经验需要经过验证，不能只不断增加规则

这里的自我改进，指的是改进项目使用的方法、案例、检索方式和辅助工具，不意味着通过几个文件就训练了底层模型参数。
我建议每次系统性改进经过四个阶段。
发现重复失败。
例如，多次出现“人物行为可以解释，但所有聪明人都使用同一种思考方式”。
提出可检验的改进假设。
例如，在写作前增加人物关注点与取舍的对照，可能比事后修改台词更有效。
用候选方法进行对照。
使用已有案例与尚未用于修改方法的案例，比较新旧方法的结果。不能只看最初触发改进的那一章。
保留、暂用或回滚。
有改善依据才推广；证据不足则标记为试验方法；出现明显退步就回滚。
经验库也需要区分：
待验证的假设 → 在特定场景有效的方法 → 获得你或读者确认的经验。

不能把“某一次写作有效”升级为“以后所有小说都必须这样写”。不同题材和读者方向，可能需要不同方法。

### 自主改进也有不可自行改写的部分

你的创作原则、明确锁定项、原始读者评价、既有基准记录，以及资源与停止边界，应放在受保护的控制范围内。
Agent 可以提出修改建议，但不能通过改写历史反馈、删除失败案例或取消必要审核，让系统看起来越来越好。
**保护不能只靠提示词。**建议让 Agent 在候选工作区修改方法与工具，由外层控制程序校验后再启用；控制程序自身的更新不能由当前运行的任务直接替换。第一版若没有完成实际权限隔离，就只能称为流程约束，不能宣称已经形成硬保护。

## 九、跨会话与换 Agent：交接的是任务状态，不是聊天摘要


### 1. 不必等上下文快满才换会话

我更推荐把工作拆成边界清晰的任务：研究一个问题、写一个场景、审查一章、修复一个跨章问题。
任务完成后保存状态，再由新会话执行下一项。较大的单项任务也要有中间检查点。
这样，长期连续工作不必依赖 Agent 精准判断“上下文还剩多少”，也不依赖它在最后一刻成功写出总结。
Codex 的 codex exec 已支持脚本调用、JSONL 事件输出和结构化结果，并默认复用已保存的 CLI 登录，可作为第一版调度的接入基础。OpenAI Developers

### 2. 每次交接必须包含可验证的信息

至少包括：任务编号、输入版本、已经完成的步骤、改动文件、审核状态、未解决问题、下一步和累计重试记录。
新会话开始时，应核对这些记录与实际文件是否一致。
**“Agent 说完成了”不是完成依据。**程序还要确认文件存在、结果格式正确、引用版本没有过期、必要检查确实运行过。
第一版建议同一本书的正式版本只有一个写入者；审核任务可以只读。需要尝试不同方案时使用候选分支，不让多个任务同时覆盖同一章。

### 3. 停止条件属于整个任务，不属于某个会话

下面这些状态不能因为新开会话而清零：
等待你的决策、额度不足、反复修改没有进展、连续工具故障、触及授权边界。

遇到这些情况，调度程序保存状态并停止，或按明确的、有限的恢复策略处理，不能无上限重试。
使用 ChatGPT 登录与使用 API key 是不同的计费路径；现有订阅仍有相应使用限制。因此第一版应固定现有订阅路径，不自动切换付费 API、不购买额外额度，也不通过换会话绕过服务限制。OpenAI Developers

### 4. 换 Agent 只换接入层，但必须重新验收

创作任务使用统一的输入输出约定，接入层负责把它转换为不同客户端能执行的操作。
Claude Code 官方也提供非交互运行和结构化输出能力，因此这种可替换设计有可用的技术基础；但实际接入仍要分别验证登录、权限、工具与输出行为，不能假定完全兼容。Claude Code
**可迁移的是资料、规则和工作协议，不是保证不同模型写出相同质量。**换 Agent 后，应先运行已有案例，确认它能正确接手，再继续正式创作。

## 十、第一版应当做小，但验证完整

我不建议第一版就建设独立网页、大型向量数据库、十几个并发 Agent，或者完整的世界模拟器。
建议先做：
一个本地项目、一套基础人物与世界记录、一个可恢复的调度器、写作与审核任务、按需研究、版本化返修，以及少量评估案例。
先用连续几章验证完整流程，仍然遵守你选择的“逐章达到阶段性质量要求再推进”。验证重点不是章数，而是下面这些能力：

| 验证方向 | 怎样检查 |
| --- | --- |
| 创作方向正确 | 你阅读正文后，能指出沉浸感、人物区分度和情感过程是否接近预期；系统能据此具体修改。 |
| 审核有用 | 在专门的测试副本中加入信息越界、动机缺口等已知问题，观察能否发现；同时检查是否把正常写法误报为错误。 |
| 返修完整 | 改动早期事件后，能够找到并修复相关的后续内容，不残留旧人物状态。 |
| 接续可靠 | 在不同步骤中断，再启动新会话，能正确恢复，不重复覆盖、不把草稿当成通过版本。 |
| 改进有依据 | 新审稿方法在对照案例中确实有帮助，而不是只让自评分提高。 |



其中，人工植入问题的测试可以验证检测能力，但不能代替正常章节的阅读评价。
衡量进步时，我会优先看：同类错误是否减少、有效审稿意见是否增加、误报是否减少、返修是否引入新问题，以及你把章节改到认可水平所需的干预是否下降。
字数、Agent 数量、运行次数、自评分，都不能单独作为成功标准。

## 最终推荐

把这套系统设计成“有原则约束、能研究、能写作、能审稿、能回滚，也能改进工作方法的创作流程”，而不是一个一键生成长篇的工具。
第一版最需要验证的是：
换掉当前对话之后，它还能准确接手；你指出一次问题之后，它能修复具体章节，并逐步学会在其他章节中发现同类问题；当它声称自己改好了，作品中确实能看到改善。

这三件事建立起来，才有继续验证百万字规模的基础。百万字应当是可靠流程逐渐扩展后的能力，而不是第一天就要求系统交出的数字。
