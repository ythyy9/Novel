# 从意见到可验证的改进

本流程连接已有 `feedback`、版本快照、定向返修和方法对照，不建立新的自动创作原则。暂不要求嵌套模型调用；云端执行者可按外部任务协议工作。

## 用户要求与当前资料边界

本次授权消息携带的用户原话，按原样保留：

> 现在先不管这个小说程序自己调用模型，现在有你在云端帮我推进就行了。

> 对的昨天已经生成一个章节了，然后我希望能做到的就是，对于我的意见或者需要修改的，不是为了修改而修改，而是要弄清楚ai在这里为什么会这么写，如果以后要避免可以怎么做，就比如我说的ai取名喜欢用沈开头，然后我给出的解决方式是根据原作来，我希望以后自己迭代也是这种模式，而不是单纯改了就行了

这是反馈流程要求和用户报告，不是本轮已阅读章节的证据。云端仓库根的 `books/`、`runtime/`、`evaluations/experiments/` 没有对应真实作品资料；`F:/Novel/README.md`、`F:/Novel/docs/evaluations.md`、`F:/Novel/docs/evaluations/` 尚有未同步本机改动，不能访问或覆盖。实际章节路径、book id、阅读版本及生成任务日志未提供；原作完整文本所在的本机 `runtime/references/` 也未同步。需要这些输入才能绑定真实意见、核查名字分布、上下文提示与参考依据。不能把工程夹具绑定成该章节，也不能依据登记摘要假装读过原作。

“按原作来”保留为用户提出的方向；具体是命名方式、角色区分还是其他迁移范围尚需结合原材料核实，不能推成照搬姓名或适用于所有作品的规则。无法从输出文本得知模型隐藏推理或内部动机。

## 最小闭环

1. `feedback BOOK --text-file FILE --revision REV` 原样保存反馈及实际阅读版本。省略 revision 仍默认当前版本；旧版本的迟到反馈应显式指定。来源只允许 author/target_reader，Agent 分析不能冒充用户意见。
2. 用 `read`、`excerpt`、`impact` 核查具体文本、状态、提示及研究来源。记录可见事实、缺失输入与替代解释；把可能的诱因写入 hypothesis，不把推测称为真实模型动机。
3. `feedback-diagnose FEEDBACK_ID SPEC.json` 追加诊断。提出有范围的预防措施及验证计划，考虑误报、风格损失和正常案例；缺资料时允许空证据列表，明确未验证。
4. 如需修文，使用原有 revise 任务和版本审核；诊断记录可引用旧版和新版。文本改动完成不意味着同类问题已解决。
5. 使用原有 `eval-create` 建立开发/留出案例对照，`eval-judge` 区分 Agent 和真人。后续再次追加诊断，将实际结果和 experiment_id 关联；无明确改善或退步应原样保留。`eval-decide` 的原有门禁不变，任何记录都不会自动修改 methods/policies。
6. `feedback-show FEEDBACK_ID` 回读原话和全部追加记录；该命令验证记录哈希、原反馈绑定、引用和实验清单绑定。备份时保留完整 runtime、books、policies、methods 及 evaluations/experiments；数据库 audit 本身不遍历这套诊断文件，恢复后另执行 feedback-show。

## 诊断输入

全部字段必填。以下是**合成示例**，不是该用户章节的诊断：

```json
{
  "evidence": [],
  "hypothesis": "可能没有核对人物可知范围；没有提示和文本证据，原因未知。",
  "prevention": "候选：先列人物可见线索，同时保留有依据的推断。",
  "scope": "仅当前合成案例；未取得真实正文。",
  "validation_plan": "比较开发与留出案例中的越界信息和正常推断；记录误报、退步及读者评价。",
  "actual_result": null,
  "experiment_id": null
}
```

有证据时，每条 evidence 必须是 `{"revision":"实际版本", "path":"manuscript/001.md", "quote":"该版本中确实存在的非空原句"}`。可以包含多个版本；程序核验同作品归属及逐字引用，并保存文件哈希。引用吻合只证明文本存在，不证明分析正确。研究外部资料须先按已有来源协议保存，再引用相应快照，不能把任意网址当已核验证据。

`actual_result: null` 表示尚未记录执行结果；非空文本只代表操作员追加的实际观察陈述，不是程序验证成功标志。不得填虚构运行或读者意见。experiment_id 非空时必须指向已存在且可验证的对照记录，保存当时 summary（含各来源评价、保留阻塞及决策），后来的判断不会改变旧 summary；新增结论要再追加。关联本身不证明实验针对这条意见，语义相关性须复核。

存储位置为 `runtime/feedback/FEEDBACK_ID/NOTE_ID.json`，独占创建、哈希封装，不修改原反馈、不覆盖旧诊断。没有“已彻底解决”或“自动升级全局规则”字段。哈希和流程检查不是身份认证或 OS 权限隔离。
