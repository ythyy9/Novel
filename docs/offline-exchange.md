# 离线双向交接（第一阶段）

目的：两端开工前能核对另一端已做的任务、产物、版本、验证声明及未决项，避免重复劳动。当前实现本地生成、验证、接收独立副本和开工预检，**没有网络传输、实时同步或通用数据库合并**。task-claim、任务包prepare及运行入口现会检查已接收交接；操作员仍需用bundle-check查看差异并处理冲突。单端看不到离线对端的新工作，所以始终返回 peer_latest_known=false。

## 已有资料与本阶段范围

代码和工程文档走 Git；books 保存不可变版本，runtime/novel.sqlite3 保存任务/当前指针/原反馈/停止计数，runtime/feedback 保存原因与预防诊断，evaluations/experiments 保存对照。此前停写完整备份和 handoff 能恢复单份资料，但无法比较两端分叉。

本包按显式选择包含：

- 实际 handoff 任务记录：任务ID、输入/输出与当前版本、步骤、结果、停止及累计次数。相关作品的反馈原话一并保存。
- 显式指定的 UTF-8 文本产物及SHA-256、控制器源码摘要（统一换行）、控制规则摘要。
- 来源端、操作ID、共同基线包ID/状态、操作员填写的验证声明、未决项、下一步与排除项。

任务元数据由控制器读取；verification 是操作员声明，不能等同本次执行验证。单独的任意文本输入没有正式任务关联时，只选 artifacts，不伪造 book/task id。需将修改依据、诊断和实验文件逐项列入 artifacts；缺省不递归扫目录、不推定依赖齐全。包中的任务元数据和反馈也可能含私密内容，外传前必须授权整个选定范围。

本阶段不是完整备份：任务包、错误日志、认证、数据库和未选文件不打包。被允许的路径只限 books/、runtime/inputs/、runtime/feedback/、evaluations/experiments/ 下显式选定的 .json/.txt/.md；首版为跨平台采用ASCII相对路径，不允许符号链接、设备名、路径逃逸或大小写冲突。包最大16MiB，不压缩、不解压为活动目录。大规模数据继续使用已有停写备份协议。

## 本地操作

先停止资料写入者。双次捕获能检测观察到的变化，不是操作系统文件锁，也不能保障并发任意编辑的一致性。以下ID/路径仅作格式示意：

```json
{
  "origin": "local",
  "operation_id": "handoff-001",
  "task_ids": ["实际任务ID"],
  "artifacts": ["runtime/inputs/example.txt"],
  "verification": "未运行验证，待补证据",
  "unresolved": ["第二版修改依据尚未提供"],
  "next_step": "先核对对端任务与版本，再安排工作",
  "excluded": ["未选择的正文、完整原作、日志、认证与数据库"]
}
```

```text
python -m novel --root DATA bundle-create SPEC.json NEW-PACKAGE.json
python -m novel --root DATA bundle-create NEXT-SPEC.json NEXT-PACKAGE.json --baseline BASE-PACKAGE.json
python -m novel --root PEER-DATA bundle-check NEXT-PACKAGE.json --baseline BASE-PACKAGE.json
python -m novel --root PEER-DATA bundle-receive NEXT-PACKAGE.json --baseline BASE-PACKAGE.json
```

每次新的交接用新 operation_id；重复接收同一个包幂等。同来源/操作ID对应不同包内容则拒绝。输出文件独占创建，已有包不会被覆盖。先通过当前获准渠道交换包及共同基线；**上述命令不执行交换动作**。没有选定目的地和传输授权时只生成合成测试包。

返回方向使用完全相同的命令，只更换 origin/operation_id；收件箱记录在 `runtime/exchange/inbox/ORIGIN/OPERATION.json`，断网仍可读取并预检。receive 返回收到副本的回执，不表示活动状态已采用或对端已收到回执；如需对端确认，仍须经授权渠道交付该回执。保存的包携带创建时间，文件哈希只检测完整性，不认证发送者身份。

## 预检与不覆盖约束

| status | 含义与下一步 |
| --- | --- |
| same_selected_state | 所选状态一致，仍须检查已完成任务和排除项，不代表全项目已同步 |
| unknown_baseline | 无可核验共同基线；不得猜测哪端更新 |
| incoming_ahead | 接收端仍是基线、来包已变化；先核对和接续，不重做旧任务 |
| local_ahead | 来包仍是基线、接收端已变化；保留本端工作，向对端交接 |
| diverged | 双端状态不相同且均非基线，或本端缺必要状态；停止覆盖，先人工核对 |

必须显式提供可信基线包才能判断前进/分叉；不能只信来包自述的基线。后续包的任务/产物选择集须保持一致，否则拒绝建立继承关系，要求重新明确基线。首版按整个选定状态保守判冲突，不自动合并不同文件的并发修改。

work_blockers 提示版本需核对、已完成任务不得重做、停止条件必须保留。incoming_completed_tasks/incoming_stopped_tasks 便于执行者识别。即使发生分叉，receive也只保留独立证据副本；它不会改本端任务、作品、反馈、规则或“当前版本”指针。核对一次后本地状态可能再变化，所以每次开工会重新检查未处理交接；不能把手动预检报告作为持久许可。

## 验收与待接通部分

合成的两个独立资料目录验证：双向预检、共同基线、落后/分叉识别、已完成任务提示、反馈和停止记录保留、重复包幂等、同操作异内容拒绝、损坏/错误基线/路径拒绝、源变化拒绝、断开来源后读取副本、CLI输入输出。不将这些测试称为真实电脑与云端同步打通。

传输目的地和回执交付仍需授权；受限的活动资料接续见下节。用户电脑当前离线，未访问。第一版章节仅是历史输入，第二版和本地修改依据未到；没有自动把这些资料加入 Git 或交接包。


## 实际开工门禁

Engine.claim在认领事务内扫描收件箱；prepare及运行入口在执行前再次检查，覆盖先认领、后收到新证据的情况。无收件箱保持已有行为。同作品的对端completed/cancelled任务ID不能重做；未处理的running/submitted/blocked/exhausted任务阻止该作品开工。选定状态不同（包括落后、分叉、未知基线）均保守阻止，不能靠漏传--baseline绕过。无法绑定作品的纯产物包保守检查所有作品。损坏/串用收件箱拒绝开工。

选定状态相同且无阻塞时，exchange.baseline_checked事件与认领在同一事务提交；认领失败时事件也回滚。已核对的旧包不因后续正常本地进展永久阻塞，新包仍需重新检查。历史完成/取消任务ID禁止重做不因核对事件失效。明确继承已接收包的后继包可替代旧状态，但必须校验基线内容、相同选择集和累计次数不减少；并发分支都保留，不能仅按时间取最新。对同一任务的历史完成记录仍优先保留。

receive与claim使用同一SQLite写事务序列化发布收件箱和认领，接收中断留下的损坏包会拒绝开工。已认领的工作不被事后收件自动终止；准备/执行前会重查，运行开始后的跨端协调仍需交接协议。没有分布式锁，不保证两个离线端在未收到对方新包时绝不同时认领。手动改写/删除收件箱不在控制器完整性承诺内。

当前没有“一键忽略冲突”。应核对资料、保留停止和计数，明确同步选定状态或接收可验证的后继包后再认领；实际传输与通用活动合并仍需另外授权与实现；下述单任务接续不执行合并。门禁不会改正文、自动合并、自动恢复任务或清零次数。


## 显式接续单任务待审核结果

`bundle-apply` 是独立的明确写入动作，receive仍只收副本。最小范围仅支持共享任务ID、共同输入快照上完成的一个write/revise任务；包不得附带其他artifacts，本地必须已有该queued任务且没有结果。不是把任意章节文件直接变成最新版，也不自动创建作品、任务或作者决定。

```text
python -m novel --root DATA bundle-apply RECEIVED.json TASK_ID --baseline BASE.json --expected-base INPUT_REV --expected-target OUTPUT_REV
```

必须先receive同一个包。基线包内容/当前本地选定状态/任务指令/控制规则全部吻合；显式输入和目标版本与远端完成结果对应；远端也不能已推进到其他版本。其他未协调收件仍阻止接续。新增本地反馈、活动/停止任务、目标错误、次数回退或超限均拒绝，没有force选项。

结果重新经过原submit/publish的结构、引用和作者决定边界校验；用本地原输入和变化内容重算完整目标快照哈希，必须等于明确目标。复用publish内部路径，仅创建draft，不导入远端accepted状态或审核记录。原输入快照和反馈原话不改；远端新增反馈仍保留在收件证据，不自动冒充本地反馈输入。

新生成的包格式为v2，额外携带选定任务完整事件记录并计入状态哈希。v1可读取检查，但因缺失败事件不允许apply；需要双方用当前代码重新导出共同基线和后续包，不把旧包自动改成v2。远端事件保存为exchange.peer_event，包含来源包ID和原事件全字段；不复用远端SQLite自增ID，也不删除本地事件。累计尝试/no_progress取远端单任务链的值，必须不低于本地且符合本地限额；共享历史不重复累加。

快照持久化、任务完成、当前指针及接续事件在一个SQLite事务中发布。失败回滚数据库，已落盘完整孤立快照可在相同重试时验证复用；不承诺清理所有孤立文件。相同包/任务/目标的重试通过exchange.applied识别，不重复事件或切回旧版本；不同包不能覆盖已有任务结果。接续完成记录已核对该包，后续任务可沿当前版本继续，未知新交接仍需检查。

这是有共同基线的单任务接续，不是双向数据库自动合并。两端本地审计事件与updated_at可不同，不能因正文相同宣称全部状态已同步；后续共同基线仍需明确核对。当前只在合成目录验证，未对历史第一版或未知第二版执行。

## 采用确认与下一个共同基线

采用不是作者批准。新增三步均只生成/核对本地文件，不发送数据：

```text
# B确已apply A的包后，产生采用回执
python -m novel --root B bundle-receipt A-RESULT.json B-RECEIPT.json
# A取得该回执，核对自身仍是导出时状态，并生成确认
python -m novel --root A bundle-confirm A-RESULT.json B-RECEIPT.json AGREEMENT.json
# B取得确认，并核对本地仍与回执一致
python -m novel --root B bundle-ack A-RESULT.json B-RECEIPT.json AGREEMENT.json
```

B仅receive不能出具采用回执。缺文件、错包/错目标、源端导出后发生变化、B回执后发生分叉、任何相关活动/停止任务均阻止新的确认。共同基线必须在本端登记exchange.agreement_registered后才能用于下一轮；仅拿到一个确认文件不够。A登记表示源端已确认，B登记表示确认已送达该端，不宣称A已获知B的登记或实时在线。

两端登记同一agreement ID，但保留各自完整审计。比较的共同状态包括作品版本、任务身份/指令/输入/结果/状态/累计次数、反馈内容、控制版本和选定产物；排除各端updated_at/created_at等任务时钟、历史detail和事件行差异。原包与回执仍保留这些原字段，不删改它们以求数据库相同。原始反馈保持完整比较，不能把新的作者意见忽略成“只是审计差异”。哈希不是身份签名，文件仍需经用户授权的可信渠道交付。

新共同基线只允许下一项单任务revise：必须从确认的同作品版本开始、完成且没有附加artifacts。B后续返修完成后，可用`bundle-create ... --baseline AGREEMENT.json`；A先receive，再用同agreement及显式输入/输出版本apply。本端尚无该新任务时，仅这条已确认基线上的revise允许在接续事务中创建其记录；不导入其他任务或作者决定。事务失败时新任务也回滚。

反向接续后可交换反向回执和确认，继续建立下一基线。重放同一确认/ack幂等，不重复登记或回退当前版本；旧基线本身不能绕过新的本地状态比较。确认文件写完而登记失败时，重试验证相同文件并补齐登记；残缺/不同内容不会被静默覆盖，应保留证据并用新路径重新输出。没有分布式事务、通用自动合并或全项目同步保证。

真实接入的范围和前置条件见 [两端接入清单](two-endpoint-checklist.md)。
